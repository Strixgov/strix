# Example Fixtures

Self-contained offline fixtures that exercise every verification state
without needing network access.

**These are test fixtures, not production records.** Every signature in
this directory is produced by a throwaway Ed25519 key whose public half
is in `test-jwks.json`. They demonstrate byte-for-byte verification
semantics; they are **not** evidence of any real Strix-governed action.

To verify production records, use the live CLI against the production
proof API:

```bash
npx @strixgov/verifier@latest 5686
```

---

## File inventory

| File | Expected outcome | What it demonstrates |
|---|---|---|
| `test-jwks.json` | — | The throwaway JWKS the fixtures sign against. Contains one public key with kid `strix-test-2026-05`. |
| `test-private-key.json` | — | The throwaway PRIVATE key, included only for reproducibility. **Zero production trust value.** Anyone can regenerate equivalent fixtures. |
| `verified.json` | `Status: VERIFIED` | A clean record + valid signature. The reference VERIFIED state. |
| `tamper-hash.json` | Signature invalid | Same record as `verified.json` with the last character of `evidenceHash` flipped. Canonical bytes diverge from what was signed. |
| `wrong-key.json` | `SIGNING_KEY_UNKNOWN` | Record claims `signingKeyId: "strix-test-9999-12"` which is not in `test-jwks.json`. |
| `mutation-signature.json` | `SIGNATURE_INVALID` | Canonical payload is correct, but the first byte of the signature has one bit flipped. Cryptographic check fails directly. |

## How to verify each fixture programmatically

The shipped CLI does not yet have a `verify-offline-evidence` subcommand
— the `receipt` subcommand is for tool-gateway receipts (a different
schema). For offline evidence-record verification, use the programmatic
API directly.

```js
import crypto from "node:crypto";
import fs from "node:fs/promises";
import { buildCanonicalPayload } from "@strixgov/verifier";

async function loadJSON(p) {
  return JSON.parse(await fs.readFile(p, "utf8"));
}

function jwkToPublicKey(jwk) {
  const raw = Buffer.from(jwk.x, "base64url");
  const spkiHeader = Buffer.from("302a300506032b6570032100", "hex");
  return crypto.createPublicKey({
    key: Buffer.concat([spkiHeader, raw]),
    format: "der",
    type: "spki",
  });
}

async function verifyFixture(path) {
  const fixture = await loadJSON(path);
  const { signature, _meta, ...record } = fixture;

  const jwks = await loadJSON("./examples/test-jwks.json");
  const jwk = jwks.keys.find((k) => k.kid === record.signingKeyId);
  if (!jwk) {
    return { status: "SIGNING_KEY_UNKNOWN", reason: `kid ${record.signingKeyId} not in JWKS` };
  }

  const publicKey = jwkToPublicKey(jwk);
  const canonical = buildCanonicalPayload(record);
  const sigBytes = Buffer.from(signature, "base64url");

  if (crypto.verify(null, canonical, publicKey, sigBytes)) {
    return { status: "VERIFIED" };
  } else {
    return { status: "SIGNATURE_INVALID" };
  }
}

// Run against all fixtures
for (const f of [
  "verified.json",
  "tamper-hash.json",
  "wrong-key.json",
  "mutation-signature.json",
]) {
  const result = await verifyFixture(`./examples/${f}`);
  console.log(`${f}: ${result.status}`);
}
```

Expected output:

```
verified.json: VERIFIED
tamper-hash.json: SIGNATURE_INVALID
wrong-key.json: SIGNING_KEY_UNKNOWN
mutation-signature.json: SIGNATURE_INVALID
```

## Regenerating the fixtures

The fixtures are generated by a reproducible script in the source
repository (see [MIRROR.md](../MIRROR.md)). To regenerate equivalents
with a fresh throwaway key:

```bash
# Source-repo command — generates a new test keypair + signs all four fixtures
node scripts/generate-public-release-fixtures.mjs

# Then validate them
node scripts/verify-public-release-fixtures.mjs
```

The second script is a sanity-check: it loads each fixture, runs the
verification, and asserts that the expected outcome matches what the
fixture's `_meta.expectedStatus` declares. If you fork the source repo
and add a new fixture type, extend the validator first.

## Why offline fixtures matter for this kind of package

A verifier whose only mode is "make a network call to a live service"
is fundamentally a thin shim over that service. Most of the value of
publishing a verifier is that **anyone can reproduce its results
without trusting the publisher's infrastructure**.

These fixtures let you:

- Audit the cryptographic math without any network dependency.
- Confirm that the CLI's "VERIFIED" output corresponds to actual
  Ed25519 verification passing — not a server-side flag.
- Test your own reimplementation in another language against a known
  reference.
- Stress-test the failure modes deliberately, without needing to
  corrupt production data.

Test-key isolation also keeps the production trust surface clean.
Nothing in this directory has any relationship to a real production
record; mixing them up at the deployment layer is structurally
impossible.
